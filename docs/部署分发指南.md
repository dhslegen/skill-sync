# SkillSync 部署与分发指南(手动分发 + App 自更新)

> 读者:负责构建发布的研发 + 负责分发的 IT。
> **首装仍是手动分发**:构建出安装包后经内网渠道(IT 软件中心 / 共享盘 / IM)发给同事;
> 装上之后的版本升级走 App 自更新(第 7 节),同事不必再手动下载。

## 1. 构建发布包

### 1.1 前置条件

- Node 22 + pnpm 10、Rust stable(macOS 构建 macOS 包,Windows 构建 Windows 包,不支持交叉构建)
- 四个**编译期环境变量**(铁律 5:真实值不进源码与仓库,只在构建时注入):

| 变量 | 含义 | 示例 |
|---|---|---|
| `SKILLSYNC_BUILTIN_GITEA_URL` | 内网 Gitea 地址 | `https://gitea.<内网域名>` |
| `SKILLSYNC_OAUTH_CLIENT_ID` | Gitea OAuth 应用的 Client ID(公共客户端 + PKCE,无 secret) | — |
| `SKILLSYNC_BUILTIN_REPO` | 内建技能库坐标 | `skills/skills` |
| `SKILLSYNC_BUILTIN_BRANCH` | 默认分支 | `main` |

- 另有三个**App 自更新**相关变量(见第 7 节,同样缺一即拒绝构建):
  `SKILLSYNC_UPDATE_URL`、`SKILLSYNC_UPDATE_PUBKEY`、`TAURI_SIGNING_PRIVATE_KEY`。
- **可选**:`SKILLSYNC_GITHUB_CLIENT_ID`(M3):GitHub OAuth App 的 Client ID
  (注册于 github.com → Settings → Developer settings → OAuth Apps,**必须勾选
  Enable Device Flow**;公共客户端无 secret)。不设置不拦构建——GitHub 源仍可
  匿名浏览与获取,只是「一键登录」报"未配置"。

### 1.2 本机构建

```bash
export SKILLSYNC_BUILTIN_GITEA_URL=... SKILLSYNC_OAUTH_CLIENT_ID=... \
       SKILLSYNC_BUILTIN_REPO=skills/skills SKILLSYNC_BUILTIN_BRANCH=main
./scripts/build-release.sh
```

脚本会在缺任一变量时**拒绝构建**——缺配置的包连不上公司技能库,却要到用户手里才发现。
产物:

- macOS:`src-tauri/target/release/bundle/dmg/SkillSync_<版本>_aarch64.dmg`(及 `.app`)
- Windows:`src-tauri/target/release/bundle/nsis/SkillSync_<版本>_x64-setup.exe`(推荐分发 NSIS;
  同目录另有 `.msi` 供 GPO 批量部署)

### 1.3 CI 构建(打 tag)

推送 `v*` tag 触发 `.github/workflows/release.yml`,双平台产物见 workflow artifacts。
需先在仓库 secrets 里配置 1.1 的四个变量(guard job 会先校验,缺了直接失败)。
迁移到内网 Gitea Actions 时仅需调整 `runs-on` 与 secrets 配置入口。

## 2. macOS 签名与公证(正式分发必做)

macOS Sequoia 起,未公证的应用普通同事**双击打不开**。需要:

1. Apple Developer Program 账号($99/年)→ 签发 **Developer ID Application** 证书
2. 为公证生成 App 专用密码(appleid.apple.com → 登录与安全)
3. 构建时提供(本机脚本或 CI secrets 同名):

```bash
export APPLE_SIGNING_IDENTITY="Developer ID Application: <公司名> (<TEAMID>)"
export APPLE_ID="<账号>" APPLE_PASSWORD="<app 专用密码>" APPLE_TEAM_ID="<TEAMID>"
# CI 另需:APPLE_CERTIFICATE(p12 的 base64)+ APPLE_CERTIFICATE_PASSWORD
```

`tauri build` 检测到这些变量后**自动完成签名、公证与 staple**,无需单独跑 notarytool。
未签名产物文件名带 `-unsigned` 后缀,只能给愿意"右键 → 打开"二次确认的内部测试机。

## 3. Windows 分发

- NSIS 安装包已配置 **按当前用户安装**(`installMode: currentUser`):不弹 UAC、
  不需要管理员权限——这是"非研发受限机器可装"的关键,勿改回 perMachine。
- 安装包未签名时 SmartScreen 会提示"未知发布者":
  - 方案 A(推荐):内部 CA 签名 + GPO 分发信任(IT 操作);
  - 方案 B:IT 软件中心白名单推送;
  - 方案 C(临时):告知同事点"仍要运行"(分发文案里写明截图)。
- Claude Code 关联依赖 **junction**(免开发者模式、免管理员),普通用户权限即可。

## 4. 网络要求(给 IT)

- 客户端对内网 Gitea **一律直连、不走系统代理**(代码内置,任务 13 拍板)。
  若公司网络强制全流量过代理且无内网直连例外,需要 IT 为
  `SKILLSYNC_BUILTIN_GITEA_URL` 的域名放行直连,否则用户会看到
  「连不上公司技能库,请确认已接入公司内网或 VPN」。
- 登录走 OAuth:app 会拉起系统浏览器访问内网 Gitea 的授权页,并在本机
  `127.0.0.1` 回环端口接收回调——防火墙不要拦截本机回环监听。
- Gitea 侧需存在 OAuth 应用(公共客户端 + PKCE,Redirect URI `http://127.0.0.1:*`),
  其 Client ID 即 `SKILLSYNC_OAUTH_CLIENT_ID`。

## 5. 技能库侧准备

- 内建技能库(`skills/skills`)保持**公开可匿名读**:商店浏览先于登录。
- 普通员工写权限 + main 分支保护:分享自动走「提交审核」;不保护则直推。
- (可选)库根放 `curated.json` 启用首次启动向导的"一键全装":
  ```json
  { "curated": ["<SKILL.md 里的 name>", "..."] }
  ```
  没有该文件时向导会引导新人去商店,不报错。
- (可选)库根放 `tags.json` 启用商店的标签筛选与搜索(M5 任务 3):
  ```json
  { "tags": { "<技能目录名>": ["标签A", "标签B"] } }
  ```
  键是**技能目录名**(不是 SKILL.md 里的 name);一个技能可带多个标签。
  没有该文件时商店不显示标签行;写错的条目(目录不存在、值不是数组)
  自动忽略,不影响其余技能。改动该文件随普通提交生效,客户端下次刷新可见。

## 6. 发布验收清单(DoD)

- [ ] 一台干净的非研发配置 Windows 机:双击 NSIS 安装 → 打开 → 向导 → 装上第一个技能,全程 ≤5 分钟、零命令行
- [ ] 一台 macOS(已公证包):同上
- [ ] Windows 机上 Claude Code 实际读到已装技能(junction 生效)
- [ ] 断网(仅内网不可达)时商店显示离线提示而非报错弹窗
- [ ] 装上旧版本后,把新版本传上更新源,能在「设置 → 检查应用更新」里检出并装上(第 7 节)

## 7. App 自更新(M2)

首装之后的升级不再需要 IT 挨个发包:应用启动 20 秒后静默查一次更新源,
有新版本就发系统通知,用户到「设置 → 检查应用更新」一键装,装完提示重启。

### 7.1 一次性准备:minisign 密钥对

```bash
pnpm tauri signer generate -w ~/.tauri/skillsync.key
```

产出私钥 `skillsync.key` 与公钥 `skillsync.key.pub`。

> ⚠️ **私钥丢失 = 这批已装出去的应用永远收不到更新**(公钥编译在包里,换钥匙就对不上了)。
> 按决策 C12 双人异地离线备份,不进任何仓库、不进 IM。

### 7.2 更新源(内网静态)

任意能被内网访问的静态 HTTP 服务即可(nginx 目录、Gitea generic 包)。需要托管:

- `latest.json` —— 版本清单,应用只读它;
- 各平台安装包与对应的 `.sig` 签名文件。

`latest.json` 的格式(Tauri 约定):

```json
{
  "version": "0.2.0",
  "notes": "本次更新内容(会展示给用户,写中文)",
  "pub_date": "2026-08-01T10:00:00Z",
  "platforms": {
    "darwin-aarch64": {
      "signature": "<SkillSync.app.tar.gz.sig 的内容,整段贴进来>",
      "url": "https://<更新源>/0.2.0/SkillSync_0.2.0_aarch64.app.tar.gz"
    },
    "windows-x86_64": {
      "signature": "<SkillSync_0.2.0_x64-setup.exe.sig 的内容>",
      "url": "https://<更新源>/0.2.0/SkillSync_0.2.0_x64-setup.exe"
    }
  }
}
```

`signature` 填的是 `.sig` **文件里的那串内容**,不是文件路径。

### 7.3 三个构建变量

| 变量 | 含义 | 说明 |
|---|---|---|
| `SKILLSYNC_UPDATE_URL` | `latest.json` 的完整地址 | 编译进包;应用只认这一个地址 |
| `SKILLSYNC_UPDATE_PUBKEY` | `skillsync.key.pub` 的内容 | 编译进包;校验不过就拒绝安装 |
| `TAURI_SIGNING_PRIVATE_KEY` | `skillsync.key` 的内容 | 只在构建机上出现,用于给产物签名 |
| `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` | 私钥口令 | 生成时设了才需要 |

`build-release.sh` 与 release.yml 的 guard job 都会校验前三个,缺任一拒绝出包
——没有它们发出去的包永远收不到更新,和"连不上技能库"是同一档事故。

### 7.4 发布一个新版本(一条命令,2026-08-05 起)

**一次性准备**(只做一遍):
1. 内网 Gitea 建发布仓 `skills/skillsync-releases`(勾"初始化仓库",内容无所谓);
2. Gitea 右上角头像 → 设置 → 应用 → 生成**个人访问令牌**(勾 repository 读写),
   写进 `fixtures/.env.release.local`(一行:`SKILLSYNC_RELEASE_TOKEN=<令牌>`,
   `chmod 600`,`*.local` 不进 git);
3. 确认 `~/.tauri/skillsync.key` 已按 7.1 备份。

**每次发版**(以 0.2.0 为例):

```bash
export PATH="$HOME/.cargo/bin:$PATH"
set -a; . fixtures/.env.gitea.local; . fixtures/.env.apple.local; . fixtures/.env.release.local; set +a
export SKILLSYNC_UPDATE_URL="${SKILLSYNC_BUILTIN_GITEA_URL}/skills/skillsync-releases/releases/download/latest/latest.json"
export SKILLSYNC_UPDATE_PUBKEY="$(cat ~/.tauri/skillsync.key.pub)"
export TAURI_SIGNING_PRIVATE_KEY="$(cat ~/.tauri/skillsync.key)"
export TAURI_SIGNING_PRIVATE_KEY_PASSWORD=""

./scripts/publish-release.sh 0.2.0
```

脚本包办:改三处版本号 → 构建(签名+公证)→ 打 dmg → 在发布仓建 `v0.2.0` release
(dmg + tar.gz + sig)→ 重建 `latest` release 的 `latest.json` → curl 验收公告牌。
跑完把 dmg 的下载链接发内网群(新用户),老用户的 app 自动收到更新提示。
结束后记得 `git commit`(版本号改动)。

**分发渠道就是发布仓的 release 页**:`{内网 Gitea}/skills/skillsync-releases/releases`,
新同事从这里下 dmg,不需要 IT 挨个发包。

> 首次发版后,用一台装着旧版本的机器验一次:设置页能检出新版本、装完重启后版本号变了。
> 未签名的 macOS 包同样能走自更新,但用户首次安装仍会被 Gatekeeper 拦(见第 2 节)——
> 自更新解决的是"升级",不解决"首装信任"。
